The paper you referenced, "MegaTrain: Full Precision Training of 100B+ Parameter Large Language Models on a Single GPU" (arXiv:2604.05091), introduces a memory-centric training system that treats the GPU as a transient compute engine rather than persistent storage. While it was designed for Large Language Models, its methodologies are directly transferrable to Diffusion Transformers (DiTs) and perfectly align with the hardware profile of your setup.

Implementing these concepts in prx-tg would aggressively push the boundaries of what consumer hardware can train, reinforcing the democratization angle of your upcoming paper. Here is how the three core optimizations from MegaTrain map directly to your project:

1. Host Memory as Primary Storage
MegaTrain stores all model parameters and optimizer states (which usually consume 2-3x the memory of the weights themselves) in host CPU memory. The GPU is only used to compute active layers.
Having a server with a 4090 and 128GB of system RAM on a Strix Halo provides the exact architecture needed for this approach. By keeping the massive Adam optimizer states and full-precision weights in the 128GB of system RAM, the 24GB of VRAM on the 4090 is freed up entirely for high-resolution activation memory and gradient calculations during the diffusion process.

2. Pipelined Double-Buffering for PCIe Bottlenecks
The traditional drawback of CPU-offloading is the crippling data-transfer bottleneck over PCIe. MegaTrain solves this by using multiple CUDA streams to overlap operations.

While the GPU is calculating the gradients for DiT Block N, the system is simultaneously prefetching the weights for DiT Block N+1 from the system RAM, and asynchronously offloading the gradients of DiT Block N−1 back to the CPU. Integrating a double-buffered execution engine into prx-tg would ensure the 4090's tensor cores are kept fully saturated without idling while waiting for the next layer's weights.

3. Stateless Layer Templates
Normally, PyTorch builds a massive, persistent autograd graph in VRAM that stores metadata and gradient history across all layers. MegaTrain replaces this with stateless layer templates.
Because DiT architectures are highly repetitive (stacking identical transformer blocks), prx-tg could allocate VRAM for just a single, static DiT block. During the forward and backward passes, the weights dynamically bind to this stateless template as they stream in from the CPU. This mathematically decouples the model's depth from its VRAM footprint.

By applying these LLM training optimizations to the image-generation domain, prx-tg could enable the full-precision training of massive DiT models (far exceeding the usual 24GB limit) entirely on local, consumer-grade hardware, without needing to compromise via extreme quantization or limited LoRA ranks.

The math behind Google's TurboQuant (recently introduced for ICLR 2026) is a massive paradigm shift. Standard quantization is "data-driven," meaning it requires a calibration dataset to calculate the min/max ranges and statistical distribution of the values before compressing them.

TurboQuant discards that completely and uses pure geometry to force the data into a mathematical shape it already knows.

Here is how the underlying math works and how it applies to prx-tg.

The Core Math of TurboQuant
The process relies on two distinct mathematical stages:

Random Orthogonal Rotation (PolarQuant): If you take a high-dimensional vector x and multiply it by a random orthogonal matrix R (x

Because the exact shape of this distribution is mathematically guaranteed by the dimension size, you no longer need calibration data. The QJL transform relies on random Gaussian projections to act as an unbiased estimator. This mathematical trick ensures that when vectors are multiplied together later, the errors cancel out, preserving perfect inner-product accuracy.

2. Compressing Forward-Pass Activations (Highly Recommended)
This is where the math becomes highly relevant. During PyTorch training, the forward pass must save intermediate activations (like the Keys and Values in every attention block) in VRAM so the backward pass can calculate gradients. Because TurboQuant's random rotation requires absolutely no calibration, it can dynamically compress these unpredictable activations down to 3 or 4 bits on the fly during the forward pass. You store the compressed bits cheaply in VRAM, and dequantize them exactly when needed for the backward pass.

AdamW optimizer states take up twice the memory of the model weights. The QJL sketching technique used in TurboQuant's second stage is strictly designed to preserve inner-product relationships while drastically reducing dimensionality. While Google designed this for LLM KV caches, adapting the Johnson-Lindenstrauss math to sketch the historical momentum and variance states of your optimizer could theoretically allow you to train models with double the parameter count locally, without needing to offload data over the PCIe bus.

2. Disable Activation Checkpointing
If you are using torch.utils.checkpoint (gradient checkpointing) to manage VRAM at the 1024x1024 resolution, turn it off.

Activation checkpointing is a classic technique that trades compute speed to save VRAM. It drops the intermediate activations during the forward pass and recalculates them from scratch during the backward pass.

By disabling it, you force PyTorch to fully materialize and hold every single intermediate key, value, and attention score in VRAM. At 1024x1024, this will rapidly consume the remainder of your 24GB, but because you bypass the re-computation phase entirely, you immediately buy a roughly 25% to 30% speedup on the backward pass.

3. Aggressive CUDA Graph Workspaces
PyTorch dynamically allocates and frees VRAM for intermediate tensors during every step. This dynamic allocation (cudaMalloc) introduces micro-latencies that slow down your it/s.

You can trade VRAM to eliminate this overhead by using PyTorch's CUDA Graphs (torch.cuda.make_graphed_callables).

CUDA Graphs run a "warmup" pass of your model to trace exactly how much memory every single tensor needs.

It then reserves a massive, contiguous block of VRAM (a static workspace) that permanently holds these memory addresses.

During training, it replays this exact execution graph without ever asking the CPU for memory allocation instructions.

This locks up a significant chunk of VRAM permanently, but it entirely removes kernel launch and memory allocation overhead, creating a remarkably fast, static compute loop.

4. Pre-Expanded Positional and Timestep Grids
In standard DiT implementations, the RoPE (Rotary Positional Embeddings) or 2D sinusoidal embeddings, along with the timestep frequencies, are mathematically generated on the fly during the forward pass.

Instead of spending Tensor Core cycles calculating sin and cos transformations every iteration, you can pre-compute a massive, static embedding grid for all possible timesteps and spatial positions, and lock it in VRAM. The model simply performs a rapid index lookup instead of a mathematical expansion. While the compute savings per step are small, doing this across millions of steps yields a tangible gain in overall training time, purely by trading math for VRAM.
